# WO-036 — Rate limiter local por chat y remitente

Estado: módulo y verificación focal listos; integración de configuración/runtime y prueba global corresponden al maestro. Sin producción, llamadas de proveedor, commits ni cambios a main/index/config.

`createRateLimiter({clock,store,windowMs=60000,maxEvents=60,cooldownMs=3000})` exporta `snapshot(event)`, `observe(event)`, `markReply(event)` y `dispose()`. Event requiere id/chatId/sender.jid; el factory no lee entorno, crea timers ni realiza I/O. Clock y TtlStore se inyectan; las cifras son defaults técnicos del factory, no una configuración productiva incorporada por esta WO. El runtime debe suministrar valores de configuración explícitos y usar store independiente en sombra.

## Semántica

snapshot es lectura del TTL actual y devuelve `{limited,blockedUntil?,cooldownUntil}`. Proyecta si el ID actual sería una admisión nueva: los primeros maxEvents IDs caben, el siguiente queda limitado; un ID ya admitido no vuelve a contar ni queda falsamente bloqueado por ser el último de la ventana. No set/touch ni incrementos al consultar; el get existente del TtlStore puede purgar una entrada expirada de forma lazy. Nunca devuelve arrays/counters internos mutables.

observe admite y registra una vez cada combinación chat/remitente/messageID. Ventana móvil de timestamps, no contador de minuto calendario: cada ID expira exactamente al cumplir windowMs. Un resultado limited incluye blockedUntil del timestamp admitido más antiguo aún vigente. IDs rechazados durante saturación no se almacenan ni amplían el bloqueo: memoria de IDs acotada a maxEvents por pareja. Esto contabiliza admisiones, no acumula peticiones denegadas. Repetir un rechazo permanece denegado sin nueva memoria; después de liberar un cupo se podrá admitir. Repetir una admisión no extiende TTL. La expiración se evalúa contra clock.now; event.receivedAt no controla la ventana.

markReply fija cooldownUntil sólo después de un envío confirmado por el caller. No cuenta otro evento ni usa un timer. Ingesta, observe y coalescing no comienzan cooldown: tres mensajes rápidos pueden agruparse en una ejecución (S12), y recién la respuesta establece el límite de frecuencia. Una consulta de cooldown expirada devuelve 0. cooldownMs=0 deshabilita cooldown. Rate y cooldown se mantienen independientes; el gate compartido interpreta ambos.

Claves JSON de chat/remitente evitan colisiones por delimitadores; no comparten cuota entre personas o chats. Una sola entrada TTL agrupa ventana/cooldown y dura hasta el más lejano de sus timestamps. El namespace rate-limiter pertenece a esta capacidad: instancias que deban ser independientes (especialmente sombra/live) requieren stores separados. dispose verifica identidad de cada bucket escrito por el factory antes de borrar; preserva namespaces ajenos y buckets sustituidos por otro factory, sin disponer el store global. Tracking propio se poda en cada escritura y el limiter puede reutilizarse después de dispose.

## Validación y límites

Opciones requieren enteros seguros: ventana/cantidad positivas y cooldown no negativo. Clock exige timestamp entero seguro y suma de expiración representable. IDs no vacíos y tamaño≤512; no infiere ni normaliza alias PN/LID, porque ingesta provee identidad canónica. Error de capacidad TTL se propaga, sin devolver admisión ficticia después de una escritura fallida. El runtime/gate no debe tratarlo como autorización positiva. Un store finito limita cantidad de parejas; la ventana limita IDs dentro de cada pareja. No hay bloqueo permanente, backoff de negocio, estado global ni despliegue.
