# WO-035 — Preparación del puente de sombra de Fase 3

Estado: bridge/runtime implementados y pruebas unitarias verificadas. **No instalado en producción por esta WO; no acredita 24 horas ni cierra Gate 3.** El maestro integra hooks y decide la activación bajo la autorización existente.

## Composición sin efectos de negocio

`src/v2/shadowBridge.js` exporta `createShadowBridge({clock,sink,config,features?,botJid?,maxPending?,decisionTimeoutMs?})`. Sólo `PIPELINE_MODE=shadow` construye estado; el default legacy no carga dependencias del pipeline. Crea TtlStore y Queue privados, NullMessenger que arroja si se invoca, historial vacío en memoria y un LLM que **únicamente devuelve planes registrados**, nunca conecta proveedores. No acepta repos de negocio, messenger real, shell, downloads, listeners pasivos ni jobs. Sólo llama `pipeline.decideOnly`, nunca executor/composer. Las features default son help/system-info; incluso el snapshot de estado falla si alguien intenta ejecutarlo.

`observeWebhook(raw)` admite inmediatamente un evento normalizado, acotado en memoria, sin esperar decisiones de negocio. Elimina envelope/raw y bytes inline; nombres quedan en memoria hasta 128 caracteres, texto hasta 16384 y texto citado hasta 4096. El clipping marca comparación desconocida, no se presenta como equivalencia. Máximo 32 eventos pendientes por default, máximo 1000 configurable por opción. Cada evidencia v1 pendiente tiene timeout de 10 segundos por Clock. Ausencia de registro, eventos agrupados sin correlación, decisiones fuera de ventana y features no portadas quedan **unknown**, nunca ignore inferido.

`recordV1Decision({chatId,messageId,kind,feature?,via?,respond?,reason?,plan?})` sólo resuelve el evento correlacionado por chat/ID exactos normalizados. Se registra una decisión de una rama real; no significa éxito de negocio. El productor debe distinguir propuesta de router, handler invocado y respuesta enviada. `plan` opcional es `{kind:'chat'|'ignore'|'intent',intent?,args?}`, copiado al registrar y retenido únicamente en memoria. Chat/ignore reales permiten replay sin plan adicional; intents necesitan plan canónico explícito y manifest habilitado. **No se adivina un intent a partir de feature.** Sin plan mapeable se conserva `recorded-plan-unavailable` y categoría unknown. El diff no acredita igualdad de argumentos: la salida del observador guarda sólo identificadores cerrados.

Webhooks `fromMe` siembran IDs salientes exactos por chat durante 10 minutos y no esperan evidencia v1 ni disparan negocio. El pipeline consulta ese cache para acreditar citas aun si el participante llega como LID. No utiliza coincidencias de texto como identidad. Las sesiones de legacy no se importan en este puente inicial: diferencias que dependen de sesión/historial deben declararse parciales hasta disponer de snapshots dedicados compatibles.

## Runtime desactivado y sidecars exclusivos

`src/services/phase3ShadowRuntime.js` no crea instancias, lee env ni realiza IO al importar. Exporta `initialize`/`install`, `observeWebhook`, `recordV1Decision`, `status`, `flush`, `stop`. `initialize` obtiene config exclusivamente del lector oficial v2, o recibe config inyectada; modo diferente de shadow retorna disabled antes de cargar bridge o filesystem. No importa dotenv ni consulta process.env directamente.

Activación exige `filename` explícito para JSONL nuevo por corrida. Creación `wx`, modo 0600, directorio 0700; un archivo existente no se reutiliza. Checkpoint separado por default `<filename>.checkpoint.json`, también creado exclusivamente, con stats/counters sin contenido de mensajes. Clock inyectado permite heartbeat cada 60 segundos; checkpoints posteriores usan write temporal y rename para evitar lectura de JSON parcial. `flush` espera observación/escrituras y actualiza checkpoint; `stop` cancela heartbeat y pendientes. El bridge congela duración al detenerse: esperar después de stop no añade evidencia.

Runtime default usa SystemClock y registra `operationalClock:true`; un Clock inyectado registra false. Ese marcador **no basta** para aprobar Gate 3: la corrida debe demostrar timestamps/heartbeats reales continuos, tráfico observado, contadores y reporte de categorías. No restaura ni concatena duraciones entre corridas. Errores del sink se contabilizan separadamente como sinkErrors; fallos de callbacks de observación no alteran resultados de v1. El maestro debe guardar/leer checkpoint al cerrar la corrida y controlar excepciones, drops y proporción unknown.

## Integración pendiente del maestro

Hook de webhook debe observar `messages.upsert` antes del retorno de `fromMe` para sembrar IDs. Hooks v1 deben registrar ramas reales usando IDs originales; command_usage con sólo seis columnas no permite join por sí solo. Registrar chat sólo después de verificar addressing/resultado; ignore sólo en su rama explícita; operaciones de comandos después de guards y admisión cuando se invoca handler. Propuestas LLM que todavía no se ejecutaron deben identificarse como propuestas. Un hook final garantiza resolver con unknown si el flujo no produjo evidencia utilizable; no transforma falta de usage en silencio. Los wrappers del runtime son best-effort y no se esperan desde v1. Ninguna nueva llamada de IA se autoriza como consecuencia de esta instrumentación.

No existe endpoint público nuevo ni cambio de comportamiento v1 en esta WO. La activación todavía requiere hooks, composición operacional, elección de ubicación por corrida y revisión del maestro. Un replay sin historial/sesiones debe figurar como comparación parcial en el reporte, incluso si no registra excepciones.
