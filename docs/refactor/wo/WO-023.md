# WO-023 / Fase 2 / Compatibilidad real de API v1 sobre DB v2

Objetivo: probar que el módulo DB legacy real lee datos escritos por los repositorios/adaptador v2 tras migración000; la lectura mediante un esquema copiado y SQL aislado no sustituye esa evidencia.

Scope: `tests/contract/storeCompatibility.test.js`, este documento. Insumos: exports reales y apertura DATA_DIR de `src/services/db.js`, lifecycle/migration/repos v2. No cambios a implementación/config/package/PROGRESS ni commits, credenciales, `.env` o producción.

Flujo de contrato:

1. Assert de ausencia de `.env` en checkout; mkdir temporal0700 y archivo `bot.db` exclusivamente allí.
2. Abrir adaptador SQLite v2 y ejecutar migration000 real con backup consistente previo dentro de ese directorio.
3. Seed con `createUsersRepo.addXp` (usuario ficticio42XP/nivel3), `createConversationRepo.append` (dos mensajes sintéticos cronológicos), inserts parametrizados v2 de dos reminders pending (uno vencido/otro futuro) y sesión cooperacha activa target100/collected25.
4. Cerrar conexión v2. Arrancar Node child por execFile absoluto, cwd directorio temporal, env explícito **solo DATA_DIR/NODE_ENV/TZ** en ejecución normal, sin heredar claves, NODE_OPTIONS ni HOME productivos. Bajo `--experimental-test-coverage`, Node instrumenta también subprocesses e inyecta `NODE_V8_COVERAGE`: se configura explícitamente a un subdirectorio coverage recién creado dentro del mismo temporal0700. El child admite esa única variable adicional y verifica valor exacto, directorio existente no symlink y padre DATA_DIR; no hereda la ruta de instrumentación arbitraria del proceso padre. El child assert de env/cwd/no `.env` protege el aislamiento antes del import.
5. Importar **el archivo real `src/services/db.js`**, sin VM, extracción, fake o stub. Assert del filename SQLite real en el directorio temporal. Usar APIs reales:
   - `getOrCreateUser`: recupera fila v2 existente, con XP/nivel/strikes íntegros.
   - `getRecentChatMessages`: recupera ambos mensajes, role/content/name/timestamp y orden exactos.
   - `getDueReminders(4000)`: selecciona únicamente reminder vencido, con identidad/status/texto intactos.
   - `getUserPendingReminders`: filtra usuario/chat y orden por vencimiento; remitente distinto devuelve vacío.
6. `db.js` no exporta una API de negocio cooperacha. Su handle **real exportado `db.get`** lee y verifica la sesión v2, como evidencia de retención de esquema/datos, sin afirmar recuperación mediante handler de juego ni S18. No se importa cooperacha ni se activan servicios.
7. APIs v1 reales `addXp`, `markReminderDelivered` y `saveChatMessage` escriben únicamente la DB temporal. `finally` cierra el handle SQLite real; child termina con marcador de éxito, sin imprimir filas ni datos de usuario.
8. Reabrir v2 y verificar lectura de XP47, reminder delivered, mensaje nuevo, versión000 preservada, cooperacha intacta e integrity_check=ok. Cleanup cierra DB y elimina directorio/backup/sidecars temporales.

Ningún dueño v1/v2 escribe simultáneamente. Logger legacy real solo emite estado/ruta temporal al stdout capturado del child; test no imprime sus filas. No dotenv, bot servers, schedulers, Evolution ni acceso a DB operativa. execFile usa código/argumentos estructurados sin shell, timeout15s y salida64KiB como límite. Los datos contienen JIDs/nombres/textos ficticios exclusivamente.

Validación ejecutada:

```sh
node --test tests/contract/storeCompatibility.test.js
```

Resultado **1 pass / 0 fail / 0 skipped**, con sqlite3 real en host. El contrato assert explícitamente el marcador emitido después del cierre v1 y ausencia de stderr. Esta prueba cubre compatibilidad bidireccional de usuarios/historial/reminders y preservación de sesión para migration000; no acredita rollback operacional del proceso, sesiones blackjack/cooperacha recuperadas por features, migraciones futuras o soak.

Estado: WO terminada, evidencia adicional para Gate2. El maestro integra el contrato en verify/reporte; no se sustituye el baseline ni se declara todo Gate2 por este test.
