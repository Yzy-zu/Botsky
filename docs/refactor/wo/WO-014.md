# WO-014 / Fase 1 / Clock, TTL, queue y scheduler

Objetivo: plataforma con ciclos de vida explícitos y tiempo inyectado, sin servicios legacy ni efectos al importar.

Scope: `src/v2/platform/{clock,ttlStore,queue,scheduler}.js`, `tests/unit/v2/{clock,ttlStore,queue,scheduler}.test.js`, este documento. Insumos revisados: plan §§3/4/7/12, ADR-001/002, execution-notes, `src/core/queue.js`, `src/services/scheduler.js`. No cambios a config/package/main/legacy ni commits.

Contratos:

- Clock JSDoc exportado: `import('./clock').Clock` con `now():number`, `setTimeout(callback,delayMs):number`, `clearTimeout(handle)`. Implementaciones `SystemClock` y `FakeClock(initialTime=0)`. Ambos sin timers al construir; FakeClock añade `advance(ms)` y `flush()` async, `pendingTimers`, `dispose()`. Tiempo en milisegundos. SystemClock registra timers unref y permite limpieza explícita.
- `TtlStore({clock,maxEntries=1000})`: `get/set/delete/touch(namespace,key,ttlMs)`, `sweep()`, `size`, `stats:{size,maxEntries,namespaces}`, `dispose()`. Claves compuestas JSON evitan colisiones; objetos sin prototipo evitan keys especiales. Expiración exacta/lazy, TTL positivo, capacidad estricta sin descartar sesiones vivas. `touch` distingue existencia incluso si valor es undefined. Ocupación por namespace es snapshot y purga expirados. `dispose` limpia y permite reutilizar la instancia. No timers ni persistencia todavía; persistencia opcional queda para repos/adaptadores posteriores.
- `TieredQueue({clock,tiers?})`: `add(userId,task(signal),tierName='heavy',taskName='Tarea',{priority,timeoutMs})`, `stats`, `stop()`, `dispose()` async. Defaults light concurrency4/maxPerUser5 y heavy2/3. `queueConfig` recibe valores MAX_QUEUE_LIGHT/HEAVY/PER_USER ya validados y conserva fallback legacy; no lee env. Por defecto maxPending100/tier, configurable. Prioridad descendente/FIFO entre iguales, conteo usuario incluye running+pending; tier desconocido usa heavy como legacy. Errores con code STOPPED/INVALID/USER_LIMIT/BACKPRESSURE/TIMEOUT. Timeout rechaza caller y aborta señal pero **no libera slot/reserva hasta finalizar realmente la tarea**; se evita sobreconcurrencia. `stop` rechaza pending y evita nuevos arranques, running drena; `dispose` espera tareas reales. Si una tarea ignora abort y nunca termina, dispose sigue esperando: no se finge cancelación efectiva.
- `Scheduler({clock,tickMs=10000,onError?})`: `register(id,intervalMs,run)->cancel`, `unregister`, `tick`, `runAllMaintenance` secuencial, `start/stop`, `dispose` async y `getRegisteredTasks`. Registro y tiempo en ms; composition root debe convertir minutos/segundos legacy. Arranque explícito, errores aislados, no overlap entre ticks/manual. Duplicados rechazados; quitar un job running impide reemplazarlo hasta que termina. `stop` retira ticker pero no cancela ejecución activa; `dispose` detiene, drena y cierra instancia. No se admite restart/register después de dispose. Reemplazo por ID y saneamiento silencioso legacy no se portan: wiring v2 valida configuración explícitamente.

Sin Map global: todos los datos pertenecen a instancias; Queue/Scheduler usan Sets de promesas de ejecución locales para drenaje. Imports solo entre módulos de plataforma y globals estándar; nada de servicios/red/DB/logs/environment.
