# WO-033 — Features mínimas e historial durable por hilo

Estado: implementación y verificación focal completadas; integración/composición, escenarios de Fase 3 y sombra corresponden al maestro. Sin producción, commits ni cambios de la migración 000 o índices compartidos.

## APIs y comportamiento

- `createHelpFeature({features})` en `features/help/manifest.js`: features es array inyectado o función que devuelve el registro vigente. Comando ayuda, alias help, public, scopes privado/grupo, tier none. Handler generado desde manifests vigentes, ordenado por nombre; oculta disabled, scope y permisos usando la misma accessPolicy central. `args.command` selecciona nombre/alias, `detail:true` muestra ejemplos. Ayuda explica peticiones naturales; no exige prefijos ni mantiene una segunda lista fija.
- `createSystemInfoFeature({getStatus})` en `features/system-info/manifest.js`: estado, aliases estadobot/status, public, ambos scopes, tier light. Puerto getStatus(signal) devuelve snapshot read-only cerrado: version, uptimeMs, queue.pending/running, sessions, ai ready/degraded/unavailable, memoryMb y details opcionales. No shell, imports legacy ni lecturas de configuración/procesos. Salida por defecto exactamente seis líneas; detail estrictamente true permite hasta 30 líneas extra del puerto confiable. Los campos desconocidos no se vuelcan. Version se restringe a etiqueta simple, cifras no finitas/negativas no se imprimen. Cancelación antes/después del snapshot y error del puerto se propagan sin éxito inventado. Reply incluye replyTo:event.id.
- `threadConversationMigration()` de `adapters/store/migrations/001-thread-conversation.js`: Migration version 001, checksum SHA-256 SQL. Sólo tabla thread_history e índices nuevos; no backfill desde chat_history, ni cambios a 000. El composition root debe pasar `[await legacyMigration(),threadConversationMigration()]` al migrate existente. El runner compartido sigue respaldando antes de mutaciones y verificando checksums; esta WO no lo modifica ni registra la migración implícitamente.
- `createThreadConversationRepo(db,clock)` de `adapters/store/repos/threadConversation.js`: append(event,role,content,{replyTo?,senderJid?}) y recentThread(chatId,senderJid,quotedId?,limit=12). Roles user/assistant; row durable con messageId, senderJid, quotedMessageId, role, content, timestamp. event.sender.jid identifica dueño del hilo; senderJid opcional identifica autor de respuesta assistant, sin cambiar dueño; user no puede reemplazar su autor. event.id debe identificar el mensaje almacenado (ID outbound real en una respuesta), no inventar un ID o asumir que el ID inbound identifica una respuesta enviada. clock.now marca persistencia.

## Selección y retención

recentThread selecciona mensajes propios, humanos que citan directamente un ID user propio en el mismo chat, y respuestas assistant del propio hilo. quotedId explícito añade sólo esa fila del mismo chat, incluso una respuesta del bot a otro usuario; nunca agrega el historial completo de ese dueño. La composición entrega la referencia normalizada/confiable del evento, no argumentos elegidos por el modelo. Selección de contexto no concede permisos.

Retención de 100 filas por pareja chat/dueño, aplicada transaccionalmente al append. No recorta a todos los participantes por un límite plano de 20 mensajes del chat. Consulta limitada a 1..100, orden cronológico estable por ID de inserción. Metadata inválida, contenido >65536 caracteres, tiempo no entero seguro y límites inválidos rechazan antes de escritura. SQL parametrizado. ID duplicado por chat/role es idempotente y conserva la primera escritura. No reinterpreta ni devuelve filas legacy sin metadata de remitente. Alcance cerrado: no infiere alias PN/LID ni autorización, no inventa sender/quoted metadata ausentes.

La selección por IDs requiere que el mensaje propio citado siga retenido; una referencia fuera de retención no recupera contenido borrado.100 por usuario limita cada hilo, no toda la población de chats/usuarios; una política de conservación global futura queda fuera de esta WO. Los details de estado son datos del puerto confiable; no deben conectarse a texto sin filtrar de proveedores/errores ni a secretos.

## Revisión de integración: selección natural y compatibilidad explícita

El maestro confirmó que manifests sin intents nunca eran seleccionables por el LLM para ayuda/estado. Se corrige declarando `help.show` → `ayuda` y `system-info.status` → `estado`; cada intent reutiliza la misma argsSchema cerrada del comando, sin lista paralela ni una heurística de frases. Cuatro tests nuevos prueban metadata, router natural real con proveedor fake que selecciona IDs declarados, router explícito real y compatibilidad de args con el validador/compositor. Esto verifica selección y contratos, no comprensión del proveedor.

Ambos comandos exponen `parseExplicit(tokens)` al contrato añadido por el maestro: sin tokens devuelve `{}`, `--detail` o `detallado` produce detail booleano. Ayuda admite un nombre de comando opcional, normalizado a minúsculas; argumentos extra/opciones desconocidas se rechazan. Esa gramática sólo se ejecuta después del prefijo técnico explícito y no interpreta conversación natural. No se devuelve `{tokens:[]}` a schemas que lo prohíben.

Estado declara ahora `allowLong:false`, de modo que el compositor aplica límite compacto y seis líneas por defecto. `detail:true` concede la excepción explícita de detalle mediante la política compartida. Help conserva allowLong para listar capacidades/documentación. Los detalles de estado siguen viniendo exclusivamente del puerto snapshot confiable, sin dump de objetos/arbitrarios ni secretos.
