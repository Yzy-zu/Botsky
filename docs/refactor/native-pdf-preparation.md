# Preparación multimodal nativa de PDF

`createContentReader()` conserva `readContent(source, { signal })` como API textual y expone `prepareContent(source, { signal })` para preparar adjuntos de imagen o PDF con su identidad. El segundo método entrega `{ inlineData, attachmentId, pageCount?, text? }`; imágenes aceptadas son JPEG, PNG y WebP. Los PDFs nativos incluyen su cantidad de páginas y se pasan completos al consumidor multimodal; la extracción textual sigue disponible por `readContent`.

La descarga usa el mismo puerto inyectado y se realiza una vez por llamada. La firma del archivo, el límite de entrada de 12 MiB, la página máxima configurada (hasta 1000), la detección de PDFs cifrados y la cancelación existentes siguen aplicándose. El método nativo valida que el ID y chat de la referencia coincidan exactamente con el mensaje actual o con el mensaje citado y que el dueño corresponda; entradas temporales se eliminan antes de devolver los bytes en base64. No requiere cambios al contrato de `readContent`.

Los casos TR-0166 y TR-0437 quedan pendientes de verificación. Al reanudar pruebas, comprobar: PDF texto y escaneado, imagen con firmas válidas y MIME discrepante, adjunto citado y actual con identidad exacta, referencias con ID/chat/autor cruzados rechazadas antes de descargar, PDF cifrado y sobre límites, abort durante descarga/procesamiento, limpieza del workspace tras éxito/error y que `readContent` conserve sus resultados textuales. La composición ya conecta `inlineData` al chat multimodal después de clasificar la solicitud, detrás del flag documents. El contenido se marca como datos no confiables y no concede herramientas ni permisos. Referencias cacheadas exigen identidad del dueño y clave original; alias sólo se conservan si vienen explícitos del proveedor. Esta implementación no cierra la paridad ni reclama los casos como portados.
